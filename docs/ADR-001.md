# ADR-001: NOVA 2.0 Modular Monolith and Migration Strategy

- **Date:** 2026-11-17
- **Status:** Approved at Gate 0 by owner
- **Decision owner:** Project owner

## Context

NOVA 1.0 is a Node.js 22 / Express 4 single-page app with `index.html`, modular browser JavaScript and a large `nova-server.txt`. It already has chat, voice, search, image, document, PWA, account and 13-mode logic. NOVA 2.0 must be bilingual, mobile-first, preserve NOVA 1.0 users/data, and avoid unnecessary infrastructure cost.

## Decision

Adopt a TypeScript modular monolith:

1. **Web:** Vite + React + TypeScript PWA; responsive Darbar UI, route-level lazy loading and Hindi/English i18n.
2. **API:** one Node.js 22 + TypeScript HTTP API; Express patterns retained where appropriate.
3. **Database/auth:** PostgreSQL + Supabase Auth with RLS and ownership checks for every user-owned record.
4. **Migrations:** Drizzle ORM with reviewed SQL; schema diff and dry-run on a separate synthetic database. Reconcile migration history before any future production migration.
5. **Validation:** Zod at API boundaries and for AI structured output.
6. **AI:** provider adapter package, versioned prompts, token/cost metering, per-user/global spend checks, timeouts, bounded retries, kill switch and eval hooks.
7. **Tests:** Vitest, Playwright and GitHub Actions; red CI blocks phase gate progression.
8. **Hosting:** isolated free staging service and separate test DB; synthetic data only. Production untouched until Phase 7 and exact `APPROVE RELEASE`.
9. **No microservices/Redis initially:** add only after measured need and approval.

## Repository layout

```text
apps/web/                 PWA frontend
apps/api/                 HTTP API, auth, jobs, mock webhook
packages/shared/          types, schemas, constants, i18n keys
packages/ai/              provider adapters, prompts, cost/spend guard
config/                   pricing, limits, feature flags
data/schemes/             curated scheme dataset
data/official_contacts.json
evals/                    task cases, rubrics and runner
docs/                     audit, parity, ADRs, data flows, runbooks
.github/workflows/        CI
render.yaml               staging blueprint only
```

## Alternatives considered

- Patch the current SPA: lower effort, but coupling and testability remain.
- Microservices: rejected for launch due to operational complexity and cost.
- Native Android app: rejected for initial launch; PWA fits current product direction.
- Replace Supabase immediately: rejected; reuse only after security/migration review.
- JavaScript-only stack: rejected; strict TypeScript and schemas are explicit requirements.

## Migration and compatibility

- Preserve local keys `nova`, `nova_t`, `nova_modes_v1`, `nova_mode_cache_v1`, `nova-cloud-sync-enabled`.
- Keep local data local by default; never silently enable cloud sync.
- Keep Supabase identity compatibility for eventual release; add reviewed `legacy_nova1_id` mapping.
- No production DB copy, real user data or production schema change during Phases 1–6.
- Move `general`/`voice` to Sakha; `document` to Sakha plus distinct Diwan Paper Reader; `schemes` to deterministic Diwan dataset; `shopkeeper` to Legacy.
- Keep seven Learn modes in Legacy until Guru is built/tested; keep builder in Legacy until Shilpi is built/tested.
- Keep NOVA Business Intelligence separate.
- No mode is silently removed; parity tests precede retirement.

## Consequences

**Benefits:** simpler operations, type safety, clear boundaries, shared UI/provider layer, mobile performance and staged rollout.

**Risks:** rebuild effort; existing Supabase migration ledger mismatch; local/cloud identity migration; free hosting is staging-only and has sleep/backup limits.

## Gate requirements

Gate 1: CI green, staging health endpoint reachable, no production secrets/data, test database isolated. ADR-001 owner approval is satisfied by Gate 0 approval; any material architecture change requires a new decision.
